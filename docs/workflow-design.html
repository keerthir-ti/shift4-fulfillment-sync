Temporal workflow design

Fulfillment Sync

Getting an approved sales order to the warehouse without waiting for a scheduled data copy, and knowing whether it arrived.

Describes the code in this repository. It runs on local simulators with synthetic data and has not been run against Oracle Fusion or Palantir Foundry.

1. The problem

After an order is approved in Oracle Fusion, warehouse staff can't see it in Fulfillment Manager for about 15–20 minutes. Oracle accepts the order immediately, then builds shipment lines in the background. Fulfillment Manager reads from Palantir Foundry, and those lines reach Foundry only through a scheduled CData snapshot of the whole table. The app receives no signal from Oracle at any point.

Delay = Oracle processing + wait for next snapshot + snapshot run time + indexing

The client raised these issues on the architecture call:

IssueWhat it means
DelayStaff wait for the next snapshot, even when Oracle finished long ago.
GrowthEach snapshot reads everything, so it slows as data grows and uses the shared Oracle REST limit.
Silent failureAn order that doesn't reach fulfillment raises nothing. Finding out means a manual check in Oracle.
ConstraintsOracle populates too many fields to write shipment lines optimistically. UIs can't read Oracle live because of REST limits and paging. Analytics still need the snapshot.

This reproduces locally with no Temporal running. With the app and simulators in Docker, 5 seconds of Oracle processing and a 60-second snapshot, a browser test saw Oracle holding the line after 5.9 seconds, while the order reached Fulfillment Manager only after 64.1 seconds. On simulated time with a 15-minute schedule, the slowest order took 17.5 minutes with no existing data and 22.3 minutes with 100,000 lines. The schedules come from the client, but the other timings are assumptions, so these aren't Shift4 measurements.

2. The proposed solution

One durable Temporal workflow follows each approved order and reconciles it. Once Oracle's shipment lines cover the order, one operation reads both systems, writes only what differs, and repeats until the shipment lines and the fulfillment order the warehouse reads both match. That single comparison handles retries, restarts, late changes and verification, and it also answers "why isn't this order here?" without opening Oracle. A scheduled sweep finds any approved order that was missed, and a scheduled audit corrects drift on delivered ones. The existing snapshot keeps running for analytics and correction, and could later run less often. Release for picking, create shipment, carriers and invoices aren't part of this phase.

IssueHow the solution answers it
DelayThe order no longer waits for a schedule. It appears soon after Oracle creates its lines, so Oracle's own processing time is the floor.
GrowthEach read covers one order, so its cost doesn't depend on the size of the table. Oracle reads share a limit across workers.
Silent failureEvery order ends with a known status and reason, overdue orders raise an alert event, and one command explains any order from live data.
Lost responses, restarts, repeatsWorkflow ID is known before any Oracle call, state survives worker restarts, and each pass reads fresh data and writes only differences, so repeating it is safe.
Customer dataRows stay inside the activities, so Temporal history holds only keys, quantities and counts.

3. Workflow design

deliverOrderToFulfillment: one per approved order

The approve action submits to Oracle, starts this workflow, then mirrors to Foundry, so a mirror failure can't hold the order back. The workflow file holds only the delivery path, with its Temporal plumbing in a separate runtime file, and all I/O happens in activities. Its ID, order-delivery:<SourceTransactionNumber>, is known before any Oracle call, so a lost response can't lose the order. USE_EXISTING makes a double click join the running workflow. ALLOW_DUPLICATE lets the sweep or a retry start again after a run has closed.

recoverySweepWorkflow and deliveryAuditWorkflow: the optional safety nets

A Temporal Schedule runs it every 15 minutes, looking back 24 hours and covering at most 100 orders. It catches what a single request can't: Temporal unavailable at approval, or a process that crashed between submit and start. Overlap is set to Skip, so a slow sweep can't pile up. Without it, the snapshot remains the fallback. A second Schedule runs the audit daily through auditDeliveredOrders, which runs recently delivered orders through reconcile again to correct drift after their workflows ended. Both run below the priority of new approvals.

Failures and edge cases

What goes wrongWhat happens
Oracle rejects the submitNo workflow starts, and the user sees the error. A 429 tells the user Oracle is busy.
Submit response lost, or a 5xxWorkflow starts as uncertain and trusts what Oracle holds.
Submit never reached OracleKeeps checking, then ActionRequired. Never a false success.
Temporal unavailable at approvalApproval succeeds, NotStarted is recorded, and the sweep starts it later.
Foundry mirror fails after submitWorkflow has already started, so the order is still delivered.
Worker restarts during a waitAnother worker continues from history, with no duplicates.
Foundry outage, or a lost write responseRetries, and the next read shows what was really written, so nothing is written twice.
Oracle changes between read and writeThe next pass sees Foundry is older and writes the current rows.
Same timestamp, different dataContent is compared too, so the row is written.
Line added, or order canceled, during the runLine added: delivery waits until it's covered. Canceled: ends as CanceledInOracle, including just before reconciling.
Lines written, but the fulfillment order missing or wrongNot delivered: the next pass writes it, and verifies it.
Row in Foundry that Oracle no longer hasRemoved, and a later snapshot doesn't bring it back. An empty Oracle answer never removes anything.
Foundry stale-object conflict (409)Retries, and a fresh read resolves it.
Expired credentialsKeeps retrying, and recovers once they're fixed.
A bad date or programming errorStops at once with the reason, rather than looking like a long wait.
Lines never appearOverdue at 30 minutes, then ActionRequired at 4 hours, with the reason recorded.
An order keeps failingThe sweep stops restarting it after 5 failed runs, and never restarts a delivered or stopped order. One order that can't start doesn't affect the others.
Oracle changes after deliveryCaught by the settle watch soon after delivery, then by the snapshot or daily audit.

4. Pros and cons

Pros

BenefitWhy it matters
No wait for a scheduleThe order appears soon after Oracle creates its lines. With the same containers and settings, approve to visible went from 64.1 seconds to 7.9 seconds, which is Oracle's 5 seconds plus the wait for the next check.
Timing no longer depends on luckOn the simulators, the wait varied from 5.5 to 20.5 seconds with the moment of approval today, and stayed at 2.1–2.2 seconds with the workflow.
Cost follows the order, not the tableEach read covers one order, so this path doesn't depend on table size. It used 8 Oracle calls for its order at 25,000 lines.
One simple, repeatable coreRetries, restarts, late changes and verification all go through one comparison, and repeating it is always safe.
Every order has an answerEach ends with a known status and reason, overdue orders raise an event, and make explain answers from live data with no manual check in Oracle.
Delivered means the warehouse can see itThe status is set only when a pass finds the lines and the fulfillment order match, and the settle watch checks once more.
Stays correct after deliveryA low-priority daily audit corrects drift, so a mistake doesn't wait for someone to notice it.
Real numbers from the first DEV runEvery order records Oracle's wait and approve to visible, which answers the biggest unknown and shows the improvement.
Customer data stays out of TemporalHistory holds keys, quantities and counts, so no Payload Codec is needed for this and large orders can't hit payload limits.
Survives failuresWorker restarts, lost responses, Foundry outages and expired credentials pause the work rather than lose it.
Operators can actOne command retries an order, and one signals all overdue orders after an outage.
Ready for Oracle eventsIf Oracle's events cover this status, they cut the wait with no redesign, and polling remains the fallback.
Low-risk rolloutOne flag returns the app to today's behaviour, the sweep is optional, and the snapshot remains the safety net.
